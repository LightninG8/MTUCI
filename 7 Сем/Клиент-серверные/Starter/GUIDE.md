## 2. Пара 1. Как устроен вертикальный срез

Это основа, без неё остальное непонятно. Раздел `groups` уже готов, поэтому его нужно
**прочитать** и запомнить цепочку:

```
браузер  →  groups.js  →  api.py  →  service.py  →  repo.py  →  SQLite
 (клик)      fetch        HTTP/JSON    правила,        SQL
                                       транзакция
```

| Файл | Что делает | Чего НЕ делает |
|---|---|---|
| `__init__.py` | создаёт Blueprint, импортирует `pages`, `api` **после** создания `bp` | |
| `pages.py` | отдаёт HTML | не ходит в БД |
| `api.py` | читает запрос, вызывает service, отдаёт JSON и статус | не пишет SQL |
| `service.py` | проверяет правила, открывает соединение, `with con:` | не знает про HTTP |
| `repo.py` | выполняет SQL через **переданное** соединение | не вызывает `commit` |
| `*.js` | рисует таблицу, обрабатывает клики, зовёт API | не формирует HTML из чужих данных строкой |

Ключевые приёмы, которые встречаются везде:

1. **`with con:`** — если блок завершился нормально, транзакция фиксируется, если было
   исключение, откатывается. Поэтому `commit` в repo не нужен.
2. **`finally: con.close()`** — `with con` соединение **не закрывает**, закрываем сами.
3. **`PRAGMA foreign_keys = ON`** — делается в `db.connect_db()` для каждого соединения.
   Без него SQLite не проверяет внешние ключи и позволит удалить группу со студентами.
4. **Исключения вместо кодов:** `ValueError` → 400, `LookupError` → 404, оба превращает в
   JSON обработчик в `app.py`. Поэтому в service достаточно `raise ValueError("...")`.
5. **`sqlite3.IntegrityError`** → переводим в `ValueError` с понятным текстом, иначе
   пользователь увидит «Ошибка базы данных».
6. **Параметры в SQL только через `?`**, никогда не склеивать строки (SQL-инъекция).

Проверка пары 1:

```bash

sqlite3 instance/journal.db

> PRAGMA foreign_keys;                 -- 1
> PRAGMA foreign_key_check;            -- пусто
```

## 4. Пара 3. Студенты

### 4.1. Что дописано в `repo.py`

`list_students(con, group_id=None, query=None)` — JOIN с группой, чтобы в таблице было
название группы, а не число:

```python
SELECT s.id, s.name, s.group_id, g.name AS group_name, s.email
FROM students AS s JOIN groups AS g ON g.id = s.group_id
[WHERE s.group_id = ?]  ORDER BY s.name, s.id
```

**Ловушка с поиском.** `WHERE name LIKE '%иванов%'` не найдёт «Иванов Алексей»: в SQLite `LIKE`
нечувствителен к регистру только для латиницы (ASCII). Поэтому группа фильтруется в SQL, а
строка поиска проверяется в Python: `needle in name.casefold()`. Это нужно уметь объяснить.

`get_student(con, id)` нужна в `save_student` (проверка существования и возврат результата).

### 4.2. Сервис

Ваш `save_student` уже содержит нужные проверки. Обратите внимание:

- `group_id` обязан быть `int` (не `bool`!). Именно поэтому в JS есть `Number(groupSelect.value)`:
  значение `<select>` всегда строка.
- Пустой email превращается в `NULL` (`email.strip() or None`). По README email необязателен.
- **Перевод между группами** — это `UPDATE students SET group_id = ?`. Оценки привязаны к
  `student_id`, а не к группе, поэтому они не теряются. Это один из пунктов демонстрации.

### 4.3. Атомарное удаление

```python
with con:
    if repo.get_student(con, student_id) is None: raise LookupError(...)
    repo.delete_grades(con, student_id)      # 1-й DELETE
    if simulate_error: raise RuntimeError    # сбой посередине
    repo.delete_student(con, student_id)     # 2-й DELETE
```

Порядок важен: сначала оценки (дочерняя таблица), потом студент, иначе внешний ключ не даст
удалить студента. Если случится сбой между двумя `DELETE`, `with con` сделает `ROLLBACK`, и
студент **и** его оценки остаются на месте. Проверяет это `check_rollback.py`.

### 4.4. `students.js`

Что в нём есть и зачем:

- `import` из `api.js` и `ui.js` — **без импорта страница молча не работает** (в консоли
  `requestJSON is not defined`). Модули подключены через `<script type="module">`.
- `loadGroups()` заполняет и фильтр, и форму через готовый `fillGroups`.
- Поиск с **задержкой 250 мс** (debounce), чтобы не слать запрос на каждую букву.
- Для поиска `busy()` не вызывается: `busy` блокирует все поля, а заблокированное поле теряет
  фокус, и печатать дальше нельзя. Это реальная ошибка, которую легко сделать.
- Счётчик `requestNumber`: если ответ на старый запрос пришёл позже нового, он игнорируется,
  иначе таблица покажет устаревший результат.
- Всё пользовательское выводится через `textContent` (готовый `cell`), не через `innerHTML`.

2. Фильтр по группе показывает 20 человек.

4. Изменить группу → в «Журнале» его оценки на месте.
5. Удалить → подтверждение → студент и оценки исчезли.

## 5. Пара 4. Журнал

### 5.1. API-контракт (из README)

| Запрос | Ответ |
|---|---|
| `GET /api/journal?group_id=1` | `{group, students, subjects, grades}` |
| `POST /api/journal/grades` `{student_id, subject_id, mark}` | `{item}`, 200 |
| `DELETE /api/journal/grades/<student>/<subject>` | 204 (повторное тоже 204) |

Ошибки: плохое поле → 400, нет группы/студента/предмета → 404.

### 5.2. Идея таблицы

Пустая ячейка = **отсутствие строки** в `grades`, а не оценка 0. Поэтому `list_grades`
возвращает только существующие оценки, а JS кладёт их в `Map` с ключом `"студент:предмет"` и
при рисовании ячейки смотрит, есть ли ключ.

### 5.3. Установка и изменение — одна операция

`service.save_grade` внутри одной транзакции:

1. проверяет `mark` (целое 2–5, не `bool`, не `4.5`, не строка `"5"`);
2. проверяет, что студент и предмет существуют (иначе 404);
3. `get_grade` → если `None`, то `INSERT`, иначе `UPDATE`;
4. возвращает сохранённую оценку.

Так клиенту не нужно знать, есть ли уже оценка. Защита от дублей — это ограничение
`UNIQUE(student_id, subject_id)` в схеме: даже при гонке двух запросов вторая вставка вызовет
`IntegrityError`.

### 5.4. Удаление

`delete_grade` проверяет, что студент и предмет существуют, затем делает `DELETE`. Если оценки
уже нет, `DELETE` просто затронет 0 строк, и ответ всё равно 204. Это и есть требование
«повторное удаление пустой оценки возвращает 204».

### 5.5. Интерфейс

- Выбор группы → `GET /api/journal?group_id=…` → таблица.
- Клик по ячейке открывает форму: выбор 5/4/3/2, «Сохранить», «Удалить оценку» (скрыта, если
  оценки нет), «Отмена».
- После записи JS **заново загружает** журнал, поэтому на экране всегда данные из БД.
- Двойки подсвечены (`.grade-button.failing`), пустые ячейки имеют знак `+`.

Проверка в браузере: поставить 5 в пустую ячейку (студенты 10, 20, … без оценок) → изменить на 3
→ удалить. Затем `python check_api.py` — раздел журнала проверяет 7 некорректных значений оценки.

## 6. Пара 5. Три SQL-отчёта

Формат: `GET /api/reports?kind=groups|no_grades|failing` → `{kind, items}`.

### 6.1. Показатели групп (`kind=groups`)

```sql
SELECT g.id, g.name,
       COUNT(DISTINCT s.id) AS student_count,
       COUNT(gr.id)         AS grade_count,
       ROUND(AVG(gr.mark), 2) AS average_mark
FROM groups g
LEFT JOIN students s ON s.group_id = g.id
LEFT JOIN grades   gr ON gr.student_id = s.id
GROUP BY g.id, g.name
```

Почему именно так (частые вопросы):

- **`LEFT JOIN`**, а не `JOIN`: иначе пустая группа пропадёт из отчёта.
- **`COUNT(DISTINCT s.id)`**: после присоединения оценок строка студента повторяется по разу
  на каждую оценку; обычный `COUNT(s.id)` посчитал бы 56 вместо 20 (54 строки с оценками и 2 студента без оценок).
- **`COUNT(gr.id)`**, а не `COUNT(*)`: `COUNT(*)` посчитает и строки без оценок.
- **`AVG`** игнорирует `NULL` и для группы без оценок даёт `NULL` → в JSON `null`, как требует README.

Ожидаемо на исходных данных: по 20 студентов, по 54 оценки в каждой группе.

### 6.2. Студенты без оценок (`kind=no_grades`)

```sql
FROM students s JOIN groups g ON g.id = s.group_id
LEFT JOIN grades gr ON gr.student_id = s.id
WHERE gr.id IS NULL
```

У студента без оценок после `LEFT JOIN` все поля `gr.*` равны `NULL`, этим и пользуемся.
Ожидаемо: **6** строк (ID 10, 20, 30, 40, 50, 60).

### 6.3. Студенты с двойками (`kind=failing`)

```sql
FROM students s JOIN groups g ON g.id = s.group_id
JOIN grades gr ON gr.student_id = s.id
GROUP BY s.id, s.name, g.name
HAVING MIN(gr.mark) = 2
```

Если у студента две двойки, обычный `WHERE mark = 2` вернул бы его дважды.
`GROUP BY` схлопывает студента в одну строку, а `HAVING` фильтрует **группы** (минимум оценок
равен 2 ⇔ есть двойка). `WHERE` фильтрует строки до группировки, `HAVING` — после. На исходных
данных получается **40** студентов (в сиде ровно 40 двоек, все у разных студентов).

### 6.4. Интерфейс

`reports.js` описывает столбцы каждого отчёта в объекте `COLUMNS` и рисует одну общую таблицу.
Средний балл выводится как `3.57`, `null` как «—».

```bash
git commit -am "Пара 5: отчёты групп, без оценок и с двойками"
```

## 8. Если что-то не работает

| Симптом | Причина и решение |
|---|---|
| `Сначала выполните python prepare_db.py` | нет `instance/journal.db` |
| Операция «пока не реализована» (501) | в функции осталась заглушка `NotImplementedError` |
| Страница пустая, в консоли `requestJSON is not defined` | в `.js` нет `import {requestJSON} from "/static/js/api.js"` |
| `Unexpected token 'import'` | в шаблоне у `<script>` нет `type="module"` |
| Ошибка 400 «Выберите группу» при сохранении студента | в JSON ушла строка `"2"`, а не число; нужен `Number(...)` |
| Удалили группу со студентами, и всё прошло | не включён `PRAGMA foreign_keys = ON` (смотрите `connect_db`) |
| `jinja2.exceptions.TemplateNotFound` | шаблон лежит не в `templates/<раздел>/index.html` внутри среза |
| `BuildError: Could not build url for endpoint 'journal.index'` | нет `pages.py` с `@bp.get("/journal")` или Blueprint не импортирует `pages` |
| Поиск не находит русские буквы | использован `LIKE`; нужен `casefold()` в Python (см. 4.1) |
| Поле поиска «залипает» после ввода буквы | на поиске вызывается `busy(true)` |
| 500 при сохранении, в терминале `sqlite3.OperationalError` | опечатка в SQL, смотрите трейс в терминале сервера |
| Ответ 204 не разбирается | не вызывайте `response.json()` для 204; `requestJSON` это уже учитывает |
| В `git status` тысячи файлов | в индекс попал `.venv`; `git rm -r --cached .venv`, проверьте `.gitignore` |
